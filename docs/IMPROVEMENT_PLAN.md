# План улучшений Star Wanderer

Пошаговый план развития игры. Цели:

- минимум дублирования кода, всё лишнее вырезано;
- максимум производительности;
- вся механика работает и подтверждена тестами, критичный код покрыт;
- единообразный интерфейс, недостающие звуки, сгенерированные изображения
  там, где они нужны (иконки и т.д.);
- масштабируемая архитектура: новая раса, модуль или событие добавляются
  без правок по всему проекту;
- больше динамики: живой мир, НПС, расширение игры **вглубь, а не вширь**.

Этапы идут строго по порядку: сначала надёжный фундамент, потом визуал,
потом новый контент. Каждый пункт — отдельная ветка от актуального `main`
и отдельный коммит. После завершения и проверок ветка сливается в `main`;
следующий пункт начинается в новой ветке. Шаг закрыт, когда выполнено
«Готово, когда», а игра в `main` остаётся работоспособной.

## Правила для всех шагов

- Перед правкой механики читать её документ в `docs/` и чек-лист в
  `SYSTEMS_MAP.md`; после — обновлять документ.
- Каждый шаг оставляет зелёными `type-check`, `lint` и `check:all`.
- Ветки, коммиты и локальные слияния в `main` разрешены пользователем.
  Перед слиянием — проверки пункта и сборка; при изменении игрового
  поведения или интерфейса — проверка затронутого сценария в браузере.
  Незавершённый или сломанный пункт не сливается. Начальное исключение:
  инфраструктура 1.1 фиксирует восемь прежних падений до исправления 1.2.
- Рефакторинг не меняет поведение: сначала тест, фиксирующий текущее
  поведение, потом перенос кода.
- Крупный шаг проходит ревью `codex-advisor`.
- Сравнение с базовой версией — через `git archive <commit>` во временный
  каталог, не через `git stash`.

### 1.4. Тесты критичного кода

Покрыть поведенческими тестами (не регэкспами по исходнику) то, где ошибка
ломает партию:

- **Бой:** урон, щиты, криты, смерть модулей и экипажа, победа и отступление,
  боссы и их способности.
- **Экономика:** покупка и продажа, цены, контракты, награды.
- **Путешествия:** топливо, прыжки, варп, доступ к тирам.
- **Сохранения:** миграции всех версий, загрузка в любом `gameMode`.
- **Наука:** открытие технологий, применение каждого бонуса.
- **Победа и поражение:** все пути победы, game over.

Каждый тест — сценарий: исходное состояние → действие → ожидаемое состояние.
Нужны фикстуры состояния (`makeGameState()`), чтобы тест не собирал стор
вручную.

**Готово, когда:** у каждой подсистемы из списка есть сценарный тест.
Ломающая правка роняет проверку.

бандла, результаты записаны в этот документ.

### 1.10. Масштабируемость

- Пройти чек-листы `SYSTEMS_MAP.md` («новая раса», «новый модуль»…) и
  сократить число мест, которые нужно править: реестры вместо `switch` по
  типам, данные в одном месте.
- Проверка `check:data` должна ловить неполную регистрацию: раса без
  музыки, модуль без иконки, событие без перевода.

**Готово, когда:** добавление расы или модуля — правка данных и переводов,
без изменений в логике и компонентах.

### 1.11. React Doctor и Fallow: аудит и устранение важных проблем

- Полный проход `npx react-doctor@latest --yes --scope full --json`:
  корректность React, hooks, производительность, доступность и безопасность.
- `npx fallow dead-code`, `npx fallow dupes`, `npx fallow health` и
  `npx fallow architecture`: неиспользуемый код и зависимости, повторы,
  сложные функции и циклические импорты. Для отчётов — `--format json`.
- Записать версии инструментов, исходные числа и список проблем по
  важности. Проверять выводы по коду, импортам, загрузчикам и игровым
  сценариям; не удалять нужный код по одному сообщению анализатора.
- Исправить все подтверждённые важные проблемы. Оставшиеся предупреждения
  сократить до минимума; каждое оставленное ограничение обосновать.
  Не отключать правила и не добавлять исключения ради хорошей оценки.
- После исправлений повторить оба аудита, `type-check`, `lint`,
  `check:all`, сборку и затронутые игровые сценарии. Зафиксировать
  сравнение до/после; недоступную оценку внешнего сервиса не подменять числом.
- Если объём большой, разбить пункт на небольшие подзадачи и ветки;
  результаты использовать для точечных исправлений 1.6–1.10 без новых
  параллельных переписываний.

**Готово, когда:** у обоих инструментов нет подтверждённых важных проблем,
оставлен минимум обоснованных предупреждений, сравнение до/после записано,
игра и проверки работают. Повторный аудит обязателен перед завершением
каждого следующего этапа; новые важные проблемы устраняются до слияния.

### 1.12. Обновление и ревизия зависимостей

- `npx npm-check-updates` (`ncu`): получить список доступных обновлений.
  Обновлять совместимыми небольшими группами через `ncu -u` с выбором
  пакетов, затем `npm install`; фиксировать `package.json` и `package-lock.json`.
  Major-обновления разбирать отдельно по документации и требованиям миграции;
  проверять совместимость React / React DOM, Next.js и ESLint-конфигурации.
- Повторно проверить `dependencies` и `devDependencies` на лишние и дублирующие
  библиотеки, используя результаты Knip и Fallow из 1.8 и 1.11. Подтверждать
  отсутствие использования по импортам, конфигурации, CLI-командам и всем
  проверочным скриптам; удалять только действительно ненужные пакеты.
- Проверить, что используемые библиотеки объявлены прямыми зависимостями,
  а не случайно доступны через транзитивную установку. Для оставленных
  дублирующих библиотек и отложенных обновлений записать причину.
- Проверить установку из lock-файла (`npm ci`), `type-check`, `lint`,
  `build`, `check:all` и затронутые игровые сценарии в браузере. Повторить
  React Doctor и Fallow после обновления, устранить новые важные замечания.
- Работать в отдельной ветке; при большом объёме разбить пункт на небольшие
  подзадачи с проверками и слиянием каждой завершённой ветки в `main`.

**Готово, когда:** зависимости обновлены до совместимых стабильных версий,
подтверждённых ненужных библиотек нет, lock-файл воспроизводим, причины
отложенных обновлений записаны, игра и все проверки работают.

## Этап 2. Визуал: интерфейс, анимации, изображения, звук

### 2.1. Дизайн-токены и единый интерфейс

- Свести 338 HEX-цветов к палитре токенов (неоновый зелёный, янтарный,
  циан, опасность, фон, рамки) в `globals.css` / Tailwind `@theme`.
- Единые примитивы: панель, кнопка (заменить 131 сырой `<button>`), вкладки,
  бейдж, прогресс-бар, тултип, модалка — в `src/components/ui`.
- Единые отступы, размеры шрифтов и состояния: hover, active, disabled,
  focus.

**Готово, когда:** в компонентах нет произвольных HEX-цветов; все кнопки и
панели собраны из примитивов.

### 2.2. Иконки вместо эмодзи

- Инвентаризация 565 эмодзи: какие стоят на месте иконок (ресурсы, вкладки,
  статусы, типы событий).
- Генерация недостающих иконок в едином пиксельно-неоновом стиле через
  AI Studio (FLUX), упаковка в спрайт-листы по образцу `icons.webp`.
- Компонент `<GameIcon id="..." />` поверх спрайтов; эмодзи остаются только
  в тексте журнала.

**Готово, когда:** ни один элемент интерфейса не использует эмодзи как
иконку.

### 2.3. Недостающие изображения

- Аудит мест без арта: события, кризисы, артефакты, боссы, контракты,
  достижения.
- Генерировать только там, где картинка несёт смысл, а не для заполнения.

### 2.4. Анимации

Все анимации — с учётом настройки `animationsEnabled`:

- появление и закрытие панелей и модалок;
- плавное изменение чисел: кредиты, топливо, репутация, урон;
- полёт корабля по карте при прыжке;
- вспышки модулей при попадании, эффект повышения уровня, плашка
  достижения;
- предпочитать CSS-анимации; JS — только для canvas.

### 2.5. Сетка корабля как цельный корабль

Сейчас сетка — набор независимых картинок модулей. Нужна визуальная система,
в которой любая допустимая компоновка выглядит как корабль:

- **Корпус под модулями:** контур корпуса строится по занятым клеткам
  (обшивка, рёбра, скосы на внешних гранях), нос и корма читаются по
  направлению из `SHIP_LAYOUT.md`.
- **Связи:** коридоры и энергомагистрали между соседними модулями, хребет
  «кабина → реактор → двигатель» визуально выделен (развить существующие
  `ship-grid-power-lines`).
- **Единый арт модулей:** одна перспектива (вид сверху), палитра, толщина
  обводки и масштаб для всех размеров (1×1, 1×2, 2×2); модуль рисуется как
  отсек корпуса, а не отдельный предмет. Перегенерировать набор по общему
  стилевому промпту и референсу.
- **Внешние детали:** двигатель даёт выхлоп с кормы, кабина — остекление на
  носу, оружейная палуба — турель на внешней стороне.
- **Состояния:** повреждён, уничтожен, обесточен, перегружен — оверлеи
  поверх арта, одинаковые для всех модулей.
- Та же система рисует корабль игрока в боевой сцене, чтобы сетка и бой
  выглядели одним кораблём.

**Готово, когда:** скриншот любой валидной компоновки читается как корабль
без подписей; тест рендерит несколько компоновок для визуальной сверки.

### 2.6. Бой: орудия, враги, анимации

- **Орудия:** у каждого типа оружия (лазер, кинетика, ракеты, плазма, дроны,
  ионная пушка, антиматерия, квантовая торпеда) — своя турель на корпусе,
  поворот к цели, вспышка выстрела, свой снаряд или луч, своё попадание.
  Сейчас различия только в эффектах снаряда (`WEAPONS.md`, «Кинематика
  боя»).
- **Враги:** вместо силуэтов — корабли в том же стиле, что и игрок (2.5),
  с видимыми модулями, по которым игрок целится. Отдельный арт для 4 типов
  налётчиков, 6 расовых стражей, 6 космических существ и 11 боссов
  (`ENEMY_TYPES.md`).
- **Попадания:** повреждение конкретного модуля видно на корпусе (искры,
  дым, пробоины), щит — отдельный слой с откликом на удар.
- **Читаемость:** выбранная цель, точность и шанс крита видны на сцене, а
  не только в панели.
- Анимации завязаны на событиях боя, а не на таймерах, чтобы пережить смену
  модели боя (см. 3.6).

**Готово, когда:** по сцене без панели понятно, кто, чем и куда стреляет и
что повреждено.

### 2.7. Звуки

- Эффекты для 10 панелей без звука: газовый гигант (давление, смена слоя),
  шторм (гром, разряды), астероиды, брошенный корабль и обломки (вскрытие),
  аномалия, сигнал бедствия, космический монстр (рёв), наука (запуск),
  достижения (фанфара).
- Фоновые шумы мест: гул станции, ветер планеты, треск шторма — тихий слой
  под музыкой.
- Второй трек для станций и планет каждой расы (сейчас по одному).
- `check:audio` проверяет, что у каждого события есть звук.

**Готово, когда:** у каждого действия игрока есть звуковой отклик.

## Этап 3. Живой мир, глубина, баланс

### 3.1. Обсуждение с пользователем (до кода)

Цель этапа — **глубина, а не ширина**: не новые типы локаций, а больше
смысла в существующих. Вопросы для обсуждения:

- Каких НПС не хватает: торговцы, пираты, патрули фракций, другие
  капитаны-соперники?
- Должны ли НПС влиять на экономику (цены, дефицит) и политику
  (отношения рас, кризисы)?
- Что игрок должен чувствовать в середине партии, где сейчас «провисает»?
- Какие механики стоит связать сильнее (например, репутация ↔ НПС ↔
  контракты ↔ кризисы)?
- Остаётся ли бой пошаговым или переходит на реальное время (см. 3.6)?

**Результат:** короткий дизайн-документ в `docs/`, согласованный с
пользователем.

### 3.2. НПС и динамика мира

Ориентировочно, после 3.1:

- Корабли НПС на карте сектора с простыми целями: торговать, патрулировать,
  грабить, бежать от кризиса. Ход НПС — часть игрового цикла.
- Мир меняется без игрока: станции растут или падают, фракции воюют, цены
  реагируют на события.
- Встречи с НПС порождают контракты, слухи и стычки, связанные с
  репутацией.
- Нагрузка: обработка НПС укладывается в бюджет хода (замер из 1.9).

### 3.3. Тесты баланса

- Симулятор партии: ботом прогнать N партий с разными seed (нужен
  детерминированный `rng` из 1.5), собрать статистику: кредиты по ходам,
  смерти, частоту побед, используемые модули и технологии.
- Отчёт: доминирующие и бесполезные стратегии, провалы прогрессии.

### 3.4. Баланс боя: все юниты и боссы

- **Профили силы игрока:** набор эталонных кораблей по стадиям партии
  (старт, тир 1, тир 2, тир 3, финал): модули, оружие, технологии, экипаж.
- **Матрица боёв:** каждый профиль против каждого врага — 4 типа налётчиков
  по уровням угрозы, 6 расовых стражей, 6 космических существ, 11 боссов.
  Для каждой пары — сотни боёв на разных seed: доля побед, средняя длина
  боя, потери модулей и экипажа.
- **Окна сложности:** для каждого врага задаётся, на какой стадии игрока бой
  должен быть честным (например, победа 50–80%), рано — опасным, поздно —
  лёгким. Тест падает, если враг выпадает из своего окна.
- **Боссы:** проверка каждой способности (воскрешение, регенерация,
  пропуск хода, гарантированный крит…) — срабатывает, не делает бой
  непроходимым при подходящей стадии.
- **Отчёт** в `docs/`: таблица «враг × стадия → доля побед», обновляется
  скриптом.

**Готово, когда:** у каждого врага и босса есть окно сложности и тест,
который его держит.

### 3.5. Скорость получения оружия

Сейчас оружие открывается цепочкой «технология → чертёж → крафт на
верфи». Если симуляции (3.3) покажут, что до интересного боя слишком долго:

- стартовое оружие разных типов в кораблях запуска;
- оружие в награду за контракты и победы, у торговцев станций;
- дешевле или раньше первые боевые технологии.

Цель: первые 30–60 минут игрок уже выбирает тактику, а не ждёт оружия.
Решение принимается по данным 3.3, а не на глаз.

### 3.6. Модель боя: пошаговый или реальное время

Вопрос для обсуждения с пользователем, а не готовое решение. Варианты:

| Модель | Плюсы | Минусы |
| --- | --- | --- |
| Пошаговый (сейчас) | продуманная тактика, работает на мобильных, уже сбалансирован | может казаться медленным |
| Реальное время с паузой (FTL-подобный) | динамика, микроуправление экипажем и энергией, хорошо ложится на сетку модулей | большой объём переделки, новый баланс, сложнее на телефоне |
| Активная шкала времени (ATB) | компромисс: перезарядка орудий в реальном времени, решения дискретные | смешанная модель сложнее объяснить |

Порядок работы: прототип выбранной модели в отдельной ветке на одном
враге → сравнение ощущений → решение. Переход возможен только после 1.4
(тесты боя), 1.5 (`rng`) и 3.4 (матрица баланса): они покажут, что новая
модель не сломала баланс. Анимации из 2.6 завязаны на событиях боя и
переживут смену модели.

### 3.7. Проверка всех бонусов и открываемых элементов

- Автотест на каждый бонус из `TECHNOLOGY_STATUS.md`: включить → значение
  изменилось ровно как описано.
- Каждое открываемое (технологии, чертежи, корабли запуска, достижения,
  аугментации) достижимо в реальной партии.
- Документ `TECHNOLOGY_STATUS.md` генерируется или сверяется автоматически.

### 3.8. Ревизия науки

- Найти пустые и дублирующиеся бонусы, технологии без влияния на решения
  игрока, слишком дорогие или дешёвые ветки (по данным 3.3).
- Сократить и углубить: меньше технологий «+10%», больше открывающих новые
  решения.

## Как использовать план

1. Берётся один следующий пункт по порядку, для него заводится ветка от `main`.
2. Крупный пункт сначала дробится на подзадачи прямо в этом документе.
3. После пункта — обновление метрик и отметка `✅` в заголовке.
4. После проверок — коммит, слияние ветки в `main` и проверка результата.
   Следующий пункт выполняется в новой ветке; несколько пунктов одновременно
   не реализуются.
